Here's a thorough code review of the Grace through Faith project based on the technical summary:

Overall Assessment
This is an impressively scoped solo/small-team project with a coherent architecture and a wide feature surface. The tech choices are sensible and the feature-to-complexity ratio is well-managed. Below is a prioritized breakdown by category.

🔴 Critical Issues (Address Before Launch)
1. No Authentication
The userId: "guest" placeholder means all user data — prayers, notes, highlights, streaks — is shared globally or silently broken in any multi-user scenario. This isn't just a missing feature; it's a data integrity risk if you deploy with real users.

Recommendation: Even a minimal local identity (UUID stored in AsyncStorage) would isolate user data correctly without requiring a full auth system. For real auth, consider Clerk or Supabase Auth — both integrate well with Expo.

2. No Rate Limiting on AI Endpoints
/api/study-guide/start, /api/verse-map/generate, /api/context/generate, etc. hit OpenAI on every cache miss. Without rate limiting, a single bad actor (or a crawler) could generate significant API cost in minutes.

Recommendation: Add express-rate-limit as middleware — a 5-line fix that protects every endpoint:

ts
import rateLimit from 'express-rate-limit';
app.use('/api/study-guide', rateLimit({ windowMs: 60_000, max: 10 }));
```

### 3. No Input Validation on Many Endpoints
Zod schemas exist but aren't applied consistently. Unvalidated inputs to SQL queries risk injection-adjacent bugs (even with an ORM, malformed data can cause unexpected behavior or crashes).

**Recommendation:** Create a small `validate(schema)` middleware and apply it at the route level — keeps validation co-located with the route and enforced uniformly.

## 🟠 High Priority (Architecture Debt)

### 4. Monolithic `server/routes.ts` (2,114 lines, 67 endpoints)
This is the single biggest maintainability risk. As the file grows, it becomes hard to find endpoints, test them in isolation, or onboard new contributors.

**Recommended split:**
```
server/routes/
  bible.ts        # /api/passage, /api/books, /api/search
  study.ts        # /api/context, /api/commentary, /api/strong
  ai.ts           # /api/study-guide, /api/verse-map, /api/chapter-context
  user.ts         # /api/notes, /api/highlights, /api/prayers
  devotionals.ts  # /api/devotionals
  kids.ts         # /api/kids
  index.ts        # mounts all routers
```

### 5. Monolithic Frontend Files
`chapter.tsx` at 1,761 lines and the study tab at 1,926 lines carry too many responsibilities. The chapter reader alone handles: verse rendering, TTS logic, voice/speed/translation pickers, verse actions, and the 4D context panel.

**Recommended decomposition for the reader:**
```
components/reader/
  VerseList.tsx
  VerseActions.tsx
  TTSPlayer.tsx
  TranslationPicker.tsx
  ContextPanel.tsx   # 4D panel
Each component becomes independently testable and navigable.

6. Five Separate AI Cache Tables
context_card, verse_map_cache, chapter_context_cache, study_guide_sessions, application_template all cache AI output but in separate schemas. This complicates cache invalidation, TTL management, and monitoring AI spend.

Recommended unified schema:

sql
ai_cache (
  id, cache_type, reference_key,
  payload JSONB, model, tokens_used,
  created_at, expires_at
)
A single table with a cache_type discriminator makes cache management, auditing, and cost tracking dramatically simpler.

🟡 Medium Priority (Quality & Resilience)
7. No Middleware Layer
Auth, logging, error handling, and validation are duplicated per-endpoint. Express middleware exists precisely for this pattern.

Minimum middleware stack to add:

ts
app.use(requestLogger());        // morgan or custom
app.use(errorHandler());         // centralized error responses
app.use('/api/ai/*', rateLimiter);
app.use('/api/ai/*', validateUser);
8. No Unit or Integration Tests
E2E via Playwright is valuable but catches issues late and is slow to run. Critical logic — the Socratic phase progression, streak calculation, commentary fetching fallback — has no isolated test coverage.

Priority test targets:

Streak calculation SQL logic (pure function, easy to unit test)
Socratic phase advancement (stateful, easy to integration test)
Commentary fetching + DB caching path (catches HelloAO API regressions)
9. Large Chapter Performance Risk
Psalm 119 has 176 verses. Without virtualized rendering, this is a guaranteed jank source on mid-range Android devices. React Native's FlatList with getItemLayout is a near-drop-in replacement for the current verse list.

10. Error Boundaries Are Too Coarse
A single top-level ErrorBoundary.tsx means any component crash reloads the whole app. Users lose their reading position, TTS state, and study session.

Recommendation: Wrap major feature areas independently — the TTS player, the 4D context panel, and the commentary tab should each fail gracefully without blowing up the reader.

🟢 Low Priority (Polish & Scalability)
11. Accessibility Gaps
testID attributes are present (good for Playwright), but there are no accessibilityLabel or accessibilityRole props. The app is currently unusable with VoiceOver/TalkBack — a significant gap for a faith-based audience that skews older.

12. Hardcoded Content Is Fine — Until It Isn't
Topic pages, music, SDA beliefs, and speaker data hardcoded in frontend files is a defensible performance choice for v1. Just document clearly that any content change requires a code deploy. If that becomes a bottleneck, a simple CMS table in Postgres would unlock admin editing without a re-architecture.

13. Commentary Content Truncated at 3,000 Characters
Matthew Henry especially can be dense. A hard truncation at 3,000 chars may cut off mid-thought. Consider truncating at the last complete sentence before 3,000 chars, or expose a "read more" pattern that fetches the full commentary on demand.

14. TTS Dual-Engine Inconsistency
expo-speech (device TTS) and gpt-audio will produce noticeably different voice quality and timing. Verse-by-verse highlight sync may drift on the OpenAI path since audio streaming and playback timing are harder to control. Worth testing explicitly on web with longer passages.

Bottom line: The core product is solid and well thought-out. The three critical fixes (rate limiting, a basic user identity, and consistent validation) should happen before any public deployment. The architectural debt in routes.ts and the two large frontend files is the most important thing to address for long-term maintainability. Everything else is refinement.
